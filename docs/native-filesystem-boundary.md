# Native filesystem producer boundary

The package exposes `@swfte/mcp-server/native-filesystem` as a separate ESM library. Importing this entry does not start the MCP server. Its `NativeFilesystem` producer uses the explicitly built `SWFTE_CF1`, wire-version 1 libc helper and an inherited directory descriptor at fd 3. Selected CLI add/sync/upgrade and MCP scaffold/sync/embed callers now opt into this producer through a lazy native writer capability in frozen source. Their source-backed file receipts use actual native readback identity; inline/render-only paths avoid native admission and physical receipts. These integrations have not been executed. Default non-native writers, code export/tree, scanner/provenance later readers, queue and other separately scoped callers remain legacy consumers. Packaging and source migration do not establish their runtime filesystem safety or complete CM-G14.

Supported runtime artifacts are Darwin arm64 and x64, with a macOS 11.0 minimum, and Linux x64 using glibc. The Linux manifest records the actual producer host's glibc version as a conservative minimum, and runtime admission requires that minimum. Linux arm64, musl/Alpine, Windows and other tuples refuse with `UNSUPPORTED_PLATFORM`. A supported host with a missing or invalid artifact refuses with `NATIVE_ARTIFACT_MISSING_OR_INVALID` before project access. Runtime does not compile, download, search PATH, select a compiler or fall back to pathname writes.

The C source is MIT licensed, carries its SPDX identifier, and ships as `native/confined-fs.c` with the package's `LICENSE`. Runtime needs only the package's standalone JavaScript library and its admitted native artifact. Native files are regular, singly linked files; executables have mode 0755 and manifests 0644. Admission checks bounded descriptor reads, manifest protocol, tuple, minimum ABI, binary length and SHA-256. The package, artifact namespace, initial root selection and operating system remain trusted.

## Build and package production

`node scripts/build-confined-fs.mjs --build-host` compiles the actual supported host tuple using an absolute trusted compiler (`/usr/bin/clang` on Darwin or `/usr/bin/cc` on Linux). The build-only `SWFTE_NATIVE_CC` can select another absolute trusted compiler. Captured C bytes are compiled without a shell. The manifest binds their SHA-256, actual producer platform/architecture/libc and actual executable bytes. CPU/container/interpreter and Darwin deployment minimum are checked independently of the manifest label. One host is never relabelled as a foreign tuple.

`.native-artifacts/<tuple>/{confined-fs,manifest.json}` is generated build cache outside `dist`, excluded from npm's explicit package files. A supported ordinary `tsup` build reuses a valid current-source host cache or genuinely rebuilds that host, then assembles admitted assets after `clean:true`. An unsupported ordinary JavaScript build skips native production, which preserves the existing Alpine Docker build without promising native capability. The standalone wrapper still refuses unsupported runtime use.

`SWFTE_NATIVE_REQUIRE_ALL=1` requires exactly the three supported tuples and never compiles to repair a missing release asset. `node scripts/build-confined-fs.mjs --validate-all` is read-only and prints `SWFTE_NATIVE_MATRIX_OK` only after every complete current-source artifact passes admission. All inputs are validated before any assembly output is written. Assembly copies those actual bytes, verifies readback hashes and writes `dist/native/assembly.json`. Directory and file checks in this build producer assume a trusted cache/output namespace; repeated checks do not establish hostile concurrent namespace confinement or close TOCTOU races. An output I/O failure can leave a partial assembly.

CI uses actual `macos-15` arm64, `macos-15-intel` x64 and `ubuntu-22.04` glibc runners and checks actual tuple identity before building. Their current-run archives preserve executable modes across artifact transfer. A strict assembly job creates one complete npm tarball. All three real consumer runners install that same tarball using genuine isolated `npm ci --ignore-scripts --offline`, then import the installed public library and execute its real helper. No workspace helper, source wrapper or dependency symlink supplies that positive control. Authored installed missing/tampered/wrong-tuple/protocol controls require refusal before project effects, and real symlink/hardlink victim controls require preservation of outside bytes. The isolated consumer adds only the existing lockfile’s exact Node declaration dependency alongside the packed module; unrelated development dependencies are removed from its temporary lock. Its actual installed TypeScript compiler checks strict NodeNext public native API, root-module and compatible deep-import declarations. Only after that positive succeeds, independent wrong-policy, wrong-bytes and missing-export consumers must fail with their expected diagnostics. No workspace compiler, declarations or dependency links provide these controls. These controls remain unexecuted.

Before final required CI verification, a separate compatibility job builds the unchanged Alpine Dockerfile locally for amd64 and arm64 without pushing. Each actual unsupported-musl container must report the package CLI version, resolve the public native library, reject native selection and root admission with typed `UNSUPPORTED_PLATFORM` and no committed-effect acknowledgement, and contain no manufactured native artifacts. This is compatibility/refusal coverage, not native musl/arm64 support, and remains unexecuted.

Release retains manual `confirm=PUBLISH` and the protected `npm-publish-prod` and `docker-publish-prod` environments. The approved npm job obtains this run's three producer archives and the exact candidate. Every clean build, including the existing `prepublishOnly` verification, inherits strict matrix assembly. Package smoke requires the full recreated tarball SHA-512/integrity to match the candidate tested on all three real runners. npm publishing keeps its confirmation guard and verification lifecycle. Docker's existing platforms and dependency on npm publication remain unchanged.

## Descriptor effects and residuals

`openRoot` holds a trusted directory descriptor. Each bounded helper operation walks relative components with descriptor-relative `openat`/`mkdirat` and `O_NOFOLLOW`; it never opens an existing target for writing or truncation. Create-only publishes a fresh inode with a link operation; authorized replacement uses a fresh inode and atomic entry replacement. Expected snapshot comparison and descriptor readback establish the reported bytes under the producer's stated assumptions. Creation respects inherited umask; replacement preserves restrictive permissions. Atomicity is per entry, not per project.

A held directory capability follows its inode if a parent or root directory is renamed. It is not a guarantee that the inode remains beneath today's pathname. Same-UID adversaries can move namespaces or hardlink/modify staged inodes; the trusted package path can also race between validation and process launch. Target comparison followed by replacement is not a kernel compare-and-swap. Concurrent target changes, same-UID attacks and multi-operation partial effects remain explicit residuals. Unknown post-launch mutator failures conservatively report possible committed effects. This producer does not implement owned-tree deletion, source licensing, source-upload consent or outbound source policy.

All new compilation, native execution, installed package, matrix, Docker and publishing controls remain **QUEUED/UNRUN** in the implementation-first phase. Source review and authored controls supply no original-outcome acceptance credit.
